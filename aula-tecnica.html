Programação Orientada a Objetos com C#

Duração sugerida: 4 horas. Ambiente: .NET 8 ou superior. Esta página assume que você já passou pela introdução conceitual — aqui entramos na sintaxe real.

Módulo 0 — O problema que a POO resolve

Antes de qualquer sintaxe, vale o código ruim:

// Código procedural: dados soltos, regras espalhadas
string nomeCliente = "Ana";
decimal saldo = 1500m;
bool contaAtiva = true;

// Regra de saque duplicada em vários lugares do sistema
if (contaAtiva && saldo >= 200m)
{
    saldo -= 200m;
}

Problemas: nada impede alguém de fazer saldo = -9999m em outro arquivo. A regra "só saca se ativa e com saldo" precisa ser reescrita toda vez. Ao adicionar "limite de saque diário", é preciso caçar todas as ocorrências.

A POO junta dados + comportamento em uma unidade que protege as próprias regras:

var conta = new ContaCorrente("Ana", 1500m);
conta.Sacar(200m);   // a regra mora dentro do objeto
Frase-chave

Objeto não é um "pacote de variáveis"; é um pedaço do sistema que sabe se comportar.

Módulo 1 — Classe e objeto

Classe é a definição (a planta da casa). Objeto é a instância (a casa construída).

public class ContaCorrente
{
    // Campo (field) — estado interno, sempre privado
    private decimal _saldo;

    // Propriedade — acesso controlado ao estado
    public string Titular { get; }
    public decimal Saldo => _saldo;   // somente leitura

    // Construtor — garante que o objeto nasça válido
    public ContaCorrente(string titular, decimal saldoInicial)
    {
        if (string.IsNullOrWhiteSpace(titular))
            throw new ArgumentException("Titular é obrigatório.", nameof(titular));

        if (saldoInicial < 0)
            throw new ArgumentOutOfRangeException(nameof(saldoInicial));

        Titular = titular;
        _saldo = saldoInicial;
    }

    public void Depositar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentOutOfRangeException(nameof(valor), "Depósito deve ser positivo.");

        _saldo += valor;
    }

    public bool Sacar(decimal valor)
    {
        if (valor <= 0 || valor > _saldo)
            return false;

        _saldo -= valor;
        return true;
    }
}

Uso:

var conta = new ContaCorrente("Ana", 1500m);
conta.Depositar(300m);

if (!conta.Sacar(5000m))
    Console.WriteLine("Saque recusado.");

Console.WriteLine($"{conta.Titular}: {conta.Saldo:C}");

Ponto de atenção: construtor é um contrato

O construtor existe para impedir que o objeto exista em estado inválido. Se é possível criar uma ContaCorrente sem titular, a classe está mal escrita.

Módulo 2 — Encapsulamento

Encapsular é esconder o como e expor o o quê.

Modificadores de acesso

Regra prática: comece tudo private e só abra o que for realmente necessário.

Propriedades: as variações que importam

public class Pedido
{
    // Auto-property com setter privado: muda só por dentro
    public decimal Total { get; private set; }

    // Somente leitura: definida só no construtor
    public DateTime CriadoEm { get; }

    // init: definida na criação do objeto, imutável depois
    public string Codigo { get; init; }

    // Propriedade com lógica (full property)
    private int _quantidade;
    public int Quantidade
    {
        get => _quantidade;
        set
        {
            if (value < 0)
                throw new ArgumentOutOfRangeException(nameof(value));
            _quantidade = value;
        }
    }

    // Propriedade calculada: não guarda estado
    public bool EstaVazio => Quantidade == 0;
}

Anti-padrão frequente

// ERRADO: isso é uma struct de dados disfarçada de classe
public class Conta
{
    public decimal Saldo { get; set; }   // qualquer um zera o saldo
}

Se toda propriedade tem get; set; público e a classe não tem métodos com regra, não há encapsulamento — é só um registro. E se for mesmo só um registro, use record:

public record Endereco(string Rua, string Cidade, string Cep);

Módulo 3 — Herança

Herança expressa uma relação "é um".

public class Funcionario
{
    public string Nome { get; }
    public decimal SalarioBase { get; }

    public Funcionario(string nome, decimal salarioBase)
    {
        Nome = nome;
        SalarioBase = salarioBase;
    }

    public virtual decimal CalcularSalario() => SalarioBase;

    public override string ToString() => $"{Nome} — {CalcularSalario():C}";
}

public class Gerente : Funcionario
{
    public decimal Bonus { get; }

    public Gerente(string nome, decimal salarioBase, decimal bonus)
        : base(nome, salarioBase)   // chama o construtor da base
    {
        Bonus = bonus;
    }

    public override decimal CalcularSalario() => SalarioBase + Bonus;
}

public class Vendedor : Funcionario
{
    private readonly decimal _comissao;

    public Vendedor(string nome, decimal salarioBase, decimal comissao)
        : base(nome, salarioBase) => _comissao = comissao;

    public override decimal CalcularSalario() => SalarioBase + _comissao;
}

virtual, override, sealed, new

  • virtual — a base permite que o método seja substituído.
  • override — a derivada substitui o comportamento.
  • sealed override — substitui e fecha a cadeia para baixo.
  • new — esconde o membro da base. Quase sempre é um erro.
public class A { public virtual void Falar() => Console.WriteLine("A"); }
public class B : A { public override void Falar() => Console.WriteLine("B"); }
public class C : A { public new void Falar() => Console.WriteLine("C"); }

A obj1 = new B();  obj1.Falar();   // "B"  → polimorfismo funciona
A obj2 = new C();  obj2.Falar();   // "A"  → new quebrou o polimorfismo

Quando NÃO usar herança

A herança acopla forte: mudar a base quebra todos os filhos. Use composição quando a relação é "tem um" ou "usa um".

// Ruim: relatório não "é uma" conexão de banco
public class RelatorioVendas : ConexaoBanco { }

// Bom: o relatório usa um repositório
public class RelatorioVendas
{
    private readonly IRepositorioVendas _repositorio;

    public RelatorioVendas(IRepositorioVendas repositorio)
        => _repositorio = repositorio;
}
Diretriz

Prefira composição à herança. Só herde quando a derivada puder substituir a base em qualquer lugar sem surpresas.

Módulo 4 — Abstração: classes abstratas e interfaces

Classe abstrata

Não pode ser instanciada e pode conter implementação parcial.

public abstract class Forma
{
    public string Nome { get; }

    protected Forma(string nome) => Nome = nome;

    // Sem corpo: obriga cada filha a implementar
    public abstract double CalcularArea();

    // Com corpo: comportamento comum reaproveitado
    public string Descrever() => $"{Nome} tem área {CalcularArea():F2}";
}

public class Circulo : Forma
{
    private readonly double _raio;

    public Circulo(double raio) : base("Círculo") => _raio = raio;

    public override double CalcularArea() => Math.PI * _raio * _raio;
}

public class Retangulo : Forma
{
    private readonly double _largura, _altura;

    public Retangulo(double largura, double altura) : base("Retângulo")
        => (_largura, _altura) = (largura, altura);

    public override double CalcularArea() => _largura * _altura;
}

Interface

Define um contrato puro, sem estado. Uma classe implementa quantas interfaces quiser.

public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}

public class NotificadorEmail : INotificador
{
    public void Enviar(string destinatario, string mensagem)
        => Console.WriteLine($"E-mail para {destinatario}: {mensagem}");
}

public class NotificadorSms : INotificador
{
    public void Enviar(string destinatario, string mensagem)
        => Console.WriteLine($"SMS para {destinatario}: {mensagem}");
}

// O serviço depende da abstração, não da implementação
public class ServicoPedido
{
    private readonly INotificador _notificador;

    public ServicoPedido(INotificador notificador) => _notificador = notificador;

    public void Confirmar(string cliente)
        => _notificador.Enviar(cliente, "Seu pedido foi confirmado!");
}

Trocar e-mail por SMS não exige tocar em ServicoPedido — esse é o ganho concreto.

há código comum a compartilharsó o contrato importa
existe estado (campos) na basenão há estado

Módulo 5 — Polimorfismo na prática

A mesma chamada, comportamentos diferentes, decididos em tempo de execução.

var equipe = new List<Funcionario>
{
    new Funcionario("Carla", 3000m),
    new Gerente("Rui", 6000m, 2000m),
    new Vendedor("Léo", 2500m, 1800m)
};

decimal folha = 0;

foreach (var f in equipe)
{
    Console.WriteLine(f);          // ToString() polimórfico
    folha += f.CalcularSalario();  // cada um calcula do seu jeito
}

Console.WriteLine($"Folha total: {folha:C}");

Repare no que não existe aqui: nenhum if (f is Gerente). Uma cascata de if/switch por tipo geralmente sinaliza polimorfismo faltando.

Sobrecarga (overload) x sobrescrita (override)

public class Calculadora
{
    // Sobrecarga: mesmo nome, assinaturas diferentes — resolvida em compilação
    public int Somar(int a, int b) => a + b;
    public double Somar(double a, double b) => a + b;
    public int Somar(params int[] valores) => valores.Sum();
}

Overload: decidido pelo compilador, pela assinatura. Override: decidido em execução, pelo tipo real do objeto.

Verificação de tipo quando é inevitável

foreach (var f in equipe)
{
    // pattern matching moderno
    if (f is Gerente { Bonus: > 1000m } g)
        Console.WriteLine($"{g.Nome} tem bônus alto.");
}

string Classificar(Forma forma) => forma switch
{
    Circulo   => "redonda",
    Retangulo => "angular",
    _         => "desconhecida"
};

Módulo 6 — Detalhes de C# que fazem diferença

static

Pertence ao tipo, não à instância. Bom para utilitários e constantes; ruim quando guarda estado global mutável.

public static class ConversorMoeda
{
    public static decimal ParaDolar(decimal reais, decimal cotacao) => reais / cotacao;
}

readonly

Campo que só pode ser atribuído na declaração ou no construtor. Use sempre que a dependência não muda.

ToString, Equals, GetHashCode

Toda classe herda de object. Sobrescrever ToString() facilita depuração; sobrescrever Equals/GetHashCode é necessário para comparar por valor em class (em record vem pronto).

Módulo 7 — Introdução ao SOLID

Apresentado aqui como direção, não como dogma.

  • S — Responsabilidade única: uma classe, um motivo para mudar. Pedido calcula o total; quem envia e-mail é outro.
  • O — Aberto/fechado: adicionar um novo meio de pagamento deve significar nova classe, não editar um switch gigante.
  • L — Substituição de Liskov: se Quadrado : Retangulo quebra ao mudar largura e altura independentemente, a herança está errada.
  • I — Segregação de interfaces: melhor ILeitor e IEscritor do que um IRepositorioCompleto com 20 métodos que ninguém implementa inteiro.
  • D — Inversão de dependência: dependa de INotificador, não de NotificadorEmail.

Projeto final — Sistema de Biblioteca

Requisitos:

  1. Item abstrato com Titulo, Codigo e CalcularMulta(int diasAtraso) abstrato.
  2. Livro, Revista e Dvd herdam de Item com regras de multa distintas.
  3. Interface IEmprestavel com Emprestar(string usuario) e Devolver().
  4. Usuario com lista de itens emprestados (limite de 3).
  5. Biblioteca que registra itens, processa empréstimos e gera um relatório polimórfico.
  6. Nenhum if que verifique o tipo do item para calcular multa.
CritérioPeso
Encapsulamento (nenhum estado público mutável indevido)25%
Uso correto de abstração e polimorfismo30%
Construtores que garantem objetos válidos20%
Composição no lugar de herança forçada15%
Legibilidade e nomes10%
 
public class Usuario
{
    private readonly List<Item> _emprestimos = new();
    public IReadOnlyList<Item> Emprestimos => _emprestimos;   // leitura protegida

    public void Emprestar(Item item)
    {
        if (_emprestimos.Count >= 3)
            throw new InvalidOperationException("Limite de empréstimos atingido.");

        _emprestimos.Add(item);
    }
}

Erros comuns para revisar em sala

  1. Classe só com get; set; público e zero comportamento.
  2. Herdar para reaproveitar código, sem relação "é um".
  3. Hierarquias com 4+ níveis de profundidade.
  4. switch por tipo espalhado pelo sistema.
  5. Construtor vazio que deixa o objeto inválido.
  6. Interface com um único implementador criada "por precaução".
  7. Expor List<T> pública — devolva IReadOnlyList<T> e ofereça métodos de modificação.
